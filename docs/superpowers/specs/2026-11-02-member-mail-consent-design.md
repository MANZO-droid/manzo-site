# 회원 메일 수신 동의 + 보유 종목 비열람 안내 — 1단계 설계서

작성: 2026-11-02 · 상태: **설계안 (구현 전, 회장님 승인 대기)**
상위 목표: 회원에게 "스터디 종목 + 내 보유 종목 알람 리포트"를 장 마감 후 하루 1통 보낸다. 이 문서는 그 **1단계(수신 동의 기록·마이페이지 동의 체크·비열람 안내 문구)** 만 다룬다.
관련 문서: `2026-10-25-member-report-addendum.md` (회원 리포트 설계, 본 문서는 "요청형"과 별개인 "정기 발송형"의 선행 단계)

## 1. 정해진 것 (회장님 결정)

- 발송 내용: 회장님이 받는 일일 리포트의 **스터디 종목** + (회원이 등록한 종목이 있으면) 그 종목의 알람 리포트(이수페타시스 메일과 같은 형식). **회장님 본인의 보유 종목 신호는 제외.**
- 발송 주기: **거래일 장 마감 후 하루 1통.**
- 수신 동의: 회원이 마이페이지에서 직접 체크한다(구두 동의는 시스템에 근거가 남지 않으므로 기존 회원 6명도 한 번씩 체크).
- 마이페이지 어딘가에 "등록한 종목 정보를 관리자가 보지 않는다"는 안내 문구를 둔다.

## 2. 이번 단계의 범위

| 포함 | 제외(다음 단계) |
|---|---|
| 동의 기록 표·함수(DB) | 회원용 메일 작성기, 발송, 스케줄 |
| 마이페이지 "메일 수신 설정" 체크 | 메일 하단 수신거부 문구, 면책 문구 |
| 비열람 안내 문구 | 개인정보 처리방침 개정(별도 확인 필요) |
| 동의 상태 읽기용 서버 조회 방법 | 관리자 화면에서 동의 현황 보기 |

이 단계가 끝나도 **메일은 한 통도 나가지 않는다.**

## 3. DB 설계 (`db/008_member_mail_consent.sql`, 추가만 하는 변경)

### 3-1. 현재 동의 상태 표 `member_mail_consent`
| 열 | 설명 |
|---|---|
| user_id uuid PK, → auth.users on delete cascade | 회원 |
| digest_consent boolean not null default false | 현재 동의 여부. **기본값 false** (미체크) |
| text_version text not null | 동의 당시 화면에 보여 준 문구 버전 (예: `v1`) |
| consented_at timestamptz | 마지막 동의 시각 |
| withdrawn_at timestamptz | 마지막 철회 시각 |

### 3-2. 동의 기록 표 `member_mail_consent_log` (덧붙이기 전용)
| 열 | 설명 |
|---|---|
| id, user_id, action(`agree`/`withdraw`), text_version, created_at | 동의·철회가 있을 때마다 한 줄 추가 |

동의의 **증명 책임은 보내는 쪽에 있으므로**, 현재 상태 표와 별도로 변경 이력을 남긴다. 이력은 수정·삭제 경로를 만들지 않는다.

### 3-3. 쓰기 경로: 함수 하나 `member_set_mail_consent(p_agree boolean, p_version text)`
- `security definer`, `auth.uid()` 본인 행만 처리. 로그인하지 않았으면 거부.
- `p_version`이 서버가 아는 **현재 문구 버전**(`v1`)과 다르면 거부(화면 문구가 낡았을 때 옛 문구로 동의가 기록되는 것을 막음).
- 상태 표를 갱신하고 로그 표에 한 줄 추가한 뒤 `{ok, agreed, at}`를 돌려준다.
- 값이 이미 같으면(이미 동의, 또 동의) 로그를 추가하지 않는다.

### 3-4. 권한 (RLS)
- 상태 표: 회원은 **자기 행 읽기만** 가능. 직접 쓰기 정책 없음(권한 회수) → 함수로만 변경.
- 로그 표: 회원 접근 없음. 서버(service role)만.
- anon(비로그인): 모두 차단.
- 메일 발송 서버는 service role로 `digest_consent = true` 인 행만 읽는다.

### 3-5. 테스트 (`db/008_..._test.sql`, 롤백 방식으로 6종)
1. 회원 A가 동의 → 상태 true, 로그 1줄
2. 같은 동의 반복 → 로그 늘지 않음
3. 철회 → 상태 false, 로그 2줄
4. 회원 A가 회원 B 행을 읽을 수 없음, 직접 `update`도 불가
5. 낡은 문구 버전으로 호출 → 거부
6. anon 호출 거부

## 4. 마이페이지 화면

### 4-1. "메일 수신 설정" 블록
- 체크박스 **기본 해제**, 다른 약관과 묶지 않음.
- 문구(`v1`):
  > (선택) 만조리서치가 보내는 **스터디 종목 리포트**와, My page에 등록한 종목이 있으면 **그 종목의 알람 리포트**를 가입 이메일로 받는 데 동의합니다. 거래일 장 마감 후 하루 1통이며, 이 체크를 해제하면 바로 중단됩니다. 투자 권유·자문이 아닙니다.
- 체크/해제 즉시 함수를 호출하고, 결과를 "○월 ○일 동의됨 / 해제됨"으로 표시. 실패하면 체크 상태를 되돌리고 안내.
- **표시 위치**: 동의는 보유 종목 기록장 권한과 무관하게 모든 로그인 회원이 할 수 있어야 한다(스터디 종목 메일은 보유 종목이 없어도 받으므로). 현재 `view-denied`("아직 이용 대상이 아닙니다") 화면에도 이 블록을 보여 주는 것을 권장 → **결정 필요(§7)**.

### 4-2. 비열람 안내 문구 (보유 종목 입력 영역 근처 + 설정 블록)
> 회원님이 My page에 등록한 종목 정보는 **관리자 화면에 표시되지 않으며, 관리자는 이를 열람하지 않습니다.** 알람 리포트는 시스템이 자동으로 만들어 보내 드립니다.

**"관리자가 볼 수 없다"고 단정하지 않는 이유**: 운영자는 데이터베이스 관리 화면에 접근할 수 있어 기술적으로는 열람이 가능하다. 사실과 다른 "불가능" 표현은 회원에게 거짓 안내가 될 수 있으므로, **현재 사실(관리자 화면에 그 기능이 없고 열람하지 않는다는 약속)** 로 쓴다. 이 약속은 실제로 지킨다 — 관리자용 보유 종목 열람 기능을 만들지 않고, 자동 처리 로그에 종목코드·이메일을 남기지 않는다(이미 적용 중).

## 5. 배포·검증 순서

1. 설계 승인 후 새 브랜치 `feat/member-mail-consent`에서 SQL·화면 작성.
2. 로컬에서 가짜 로그인으로 체크 동작·실패 처리·모바일 폭 확인.
3. **회장님 확인 후** 푸시 → PR → 병합(= 배포).
4. DB는 `008`을 운영에 **회장님 승인 후** 적용하고, 적용 직후 권한(RLS 켜짐, anon 차단, 회원 직접 쓰기 불가)을 조회로 확인.
5. 회장님 계정으로 체크 → 상태·로그 행을 확인.

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 동의 없이 메일이 나감 | 발송기는 `digest_consent = true` 만 대상으로 하도록 다음 단계에서 구현·테스트 |
| 회원이 다른 회원의 동의를 바꿈 | 함수가 `auth.uid()` 본인만 처리, 직접 쓰기 차단, 테스트 4번 |
| 문구 개정 후 옛 동의 | `text_version`을 함께 저장. 문구가 바뀌면 재동의 요구(다음 개정 시) |
| 안내 문구와 실제 불일치 | 안내는 "열람 기능 없음·열람하지 않음"으로 한정하고, 실제로 열람 기능을 만들지 않는다 |
| 법적 요건(표시 문구, 야간 발송 제한, 개인정보 처리방침) 누락 | 이 단계 범위 밖. **일반 회원 발송 전에 전문가 확인 필요** |

## 7. 회장님 결정이 필요한 것

1. 동의 블록을 **"이용 대상 아님" 화면에도 보여 줄지** (권장: 보여 줌).
2. 비열람 안내 문구(§4-2) 승인. 단정 표현 대신 "열람하지 않습니다"로 쓰는 것에 동의하는지.
3. 동의 문구(`v1`, §4-1) 승인.

## 8. 다음 단계 (참고)

2단계 회원용 메일 작성기(스터디 종목 + 회원별 알람, 금지 표현 검사) → 3단계 회장님 계정 시험 → 4단계 동의 회원 첫 발송.
발송 시각은 PC의 일일 시세 게시(`run_daily.ps1` 끝의 `publish_member_*`)가 끝난 **뒤**여야 하므로, 자동화 시 그 완료 시각 이후(예: 21:00 KST)로 잡는다.
