# 회원 종목 리포트 보완 설계서 (승인 · 생성 버튼 · 메일)

작성일 2026-10-25 · 상태: **설계 초안 — 회장님 승인 전, 구현 시작 안 함**

이 문서는 `feat/member-holdings` 브랜치의 기존 계획서
(`docs/superpowers/plans/2026-10-12-member-holdings-mypage.md`, 이하 "기존 계획서")를
**그대로 두고**, 거기에 없는 부분만 덧붙입니다.

## 0. 이 문서가 다루는 범위

| 회장님 요구 | 기존 계획서 | 이 문서 |
|---|---|---|
| 회원이 자기 종목을 한눈에 관리 | 구현됨 (My page) | 다루지 않음 |
| 무기명 매매 트렌드 | 구현됨 (익명 통계) | 다루지 않음 |
| 리포트는 **승인한 회원에게만** | 없음 ("기록장 허용" 토글만 있음) | **§3** |
| 종목 옆 **리포트 생성 버튼** | 없음 | **§4~§6, §8** |
| 리포트를 **회원 메일로 발송** | 없음 | **§7** |

### 선행 조건 (중요)
`feat/member-holdings`가 **`main`에 먼저 합쳐져야** 이 문서의 구현을 시작합니다.
`admin.html`, `api/admin-member-access.js`, `mypage.html`을 두 작업이 함께 고치면 충돌하기 때문입니다.
DB 표(`member_*`)는 이미 운영 Supabase에 적용돼 있으나, 사이트 코드는 아직 배포 전입니다.

## 1. 핵심 설계 결정 (한 줄씩)

1. **리포트는 "회원"이 아니라 "종목" 단위로 만든다.** 내용은 그 종목의 시세·차트 위치·수급·뉴스 같은
   **시장 공개 정보**뿐이고, 회원의 매수가·수량·손익은 넣지 않는다.
   - 이유 ① 회원 보유 정보가 리포트 생성 과정에 전혀 들어가지 않아 **무기명 원칙이 유지**된다.
   - 이유 ② 개인 맞춤 조언이 아니라 **일반 정보 제공**이어서 규제 위험이 낮다(법률 확인 전제, §10).
   - 이유 ③ 같은 종목·같은 날 요청은 **한 번만 생성하고 재사용**(비용·AI 호출 절감).
2. **회원은 요청만 접수하고, 생성·발송은 서버 쪽 작업이 한다.** 회원 브라우저는 메일 서비스 키를 절대 갖지 않는다.
3. **리포트 승인은 "기록장 허용"과 별도 스위치**다. 승인 스위치는 곧 **공개 관문**이기도 하다(스위치를 끄면 전체 차단).
4. **매매 의견 금지.** 매수·매도·목표가·전망 표현은 만들지도, 보내지도 않는다(§6 검사 장치).

## 2. 전체 흐름

```
회원 My page ─ 종목 옆 [리포트 받기] 클릭
   │  (RPC member_request_report: 권한·보유 여부·한도를 DB가 검사)
   ▼
member_report_requests (대기)  ──▶  Vercel API가 GitHub Actions 깨움
                                        │
                                        ▼
                          make_member_report.py (리서치자동화 저장소)
                           ├ 같은 종목·오늘 리포트가 있으면 재사용
                           ├ 없으면: 시세·지표·수급·뉴스 수집 → AI(Groq) 설명 작성 → 금지어 검사
                           ├ 회원 메일 주소를 서버 권한으로 조회
                           └ 메일 서비스로 발송 → 요청 상태를 '발송됨/실패'로 갱신
   ▼
My page 버튼이 '발송됨 (10:32)'으로 바뀜
```

## 3. 리포트 승인 (요구 3)

**DB** — `db/005_member_reports.sql` (새 파일, 기존 002~004는 수정 안 함)
- `member_feature_access`에 열 추가: `reports_enabled boolean not null default false`
- 함수 `member_has_report_access()`: `holdings_enabled`와 `reports_enabled`가 **둘 다 true**일 때만 true
  (기록장 권한이 없는 회원에게 리포트만 열어 주는 상황을 막는다).
- 기존 정책 그대로: 회원은 자기 행을 읽기만 하고, 쓰기는 관리자 API(service role)만.

**관리자 API** — 기존 `api/admin-member-access.js`를 확장 (선행 조건: 위 병합 후)
- `GET` 응답에 `reportEnabled: [user_id, ...]` 추가
- `POST` 본문에 `feature: 'holdings' | 'reports'` 추가 (생략하면 기존 동작 = `holdings`)
- 관리자 확인(`verifyAdmin`)·UUID 검사 방식은 기존 코드를 그대로 사용

**관리자 화면** — 회원 표에 열 추가: `기록장 허용` 옆에 `리포트 허용`
- 기록장이 꺼진 회원은 리포트 토글을 비활성(회색)으로 표시하고 "먼저 기록장을 허용하세요" 툴팁.

## 4. 요청 접수 표·함수 (요구 4의 앞단)

**표 `member_report_requests`**

| 열 | 설명 |
|---|---|
| `id` | uuid |
| `user_id` | 요청한 회원 (탈퇴 시 같이 삭제: `on delete cascade`) |
| `stock_code` | 6자리 종목코드 |
| `status` | `pending` → `processing` → `sent` / `error` |
| `requested_at` / `processed_at` | 시각 |
| `error_message` | 실패 사유(짧게, 개인정보 없이) |

- **메일 주소는 이 표에 저장하지 않는다.** 발송 시점에 서버가 회원 계정에서 읽는다(개인정보 최소 보관).
- 회원은 **자기 행 읽기만** 가능. 직접 INSERT/UPDATE/DELETE는 막는다(RLS + 권한 회수, 기존 방식과 동일).

**함수 `member_request_report(p_stock_code text)`** (회원이 부르는 유일한 쓰기 통로)
DB 안에서 아래를 모두 검사하고, 하나라도 어기면 오류를 돌려준다.
1. `member_has_report_access()` 가 true
2. 그 `stock_code`가 **본인의 보유 기록(`member_holdings`)에 있음** (남의 종목·임의 종목으로 요청 불가)
3. **하루 한도**: 회원당 하루 3건, 같은 종목은 하루 1건 (KST 기준) — 권장값, §11에서 확정
4. 같은 종목의 `pending`/`processing` 요청이 이미 있으면 새로 만들지 않고 그 요청을 돌려줌(중복 클릭 방지)

## 5. 생성 작업 (서버 쪽)

**어디서:** 리서치자동화 저장소의 새 GitHub Actions 워크플로 `member-report.yml` + 스크립트 `scripts/make_member_report.py`.
기존 상승률 Top10이 같은 저장소에서 같은 방식(뉴스 수집 → Groq 작성 → Supabase 저장)으로 돌고 있어, 도구·키를 그대로 재사용합니다.
> 미확인: 이 PC에서 리서치자동화 저장소 폴더를 열 수 없어, 실제 파일 구조와 `collect_gainers.py`의 재사용 가능한 함수는 구현 첫 단계에서 확인합니다.

**깨우는 방법 (2중 장치)** — 기존 `api/cron-trigger-gainers.js`와 같은 이유(GitHub 자체 스케줄은 가끔 누락)
1. 즉시: 요청 접수 직후 Vercel API(`/api/member-report-kick`)가 `workflow_dispatch`로 워크플로를 깨운다.
   회원 토큰 검증 후, 대기 요청이 있을 때만 호출한다(아무나 반복 호출해도 GitHub를 두드리지 못하게).
2. 안전망: `vercel.json`에 10분마다 도는 cron 추가 — 대기 요청이 30분 넘게 남아 있으면 다시 깨운다.

**처리 순서 (스크립트)**
1. `pending` 요청을 `processing`으로 바꾸며 가져온다(두 번 처리 방지: 상태 조건부 UPDATE).
2. 종목 단위로 묶는다. 오늘자 `member_stock_reports`에 이미 있으면 재사용, 없으면 새로 만든다.
3. 새로 만들 때: `member_prices`(종가·이동평균·52주 고저), 수급 데이터, 최근 뉴스 헤드라인을 모아 AI에 넘기고 설명문을 받는다.
4. §6 검사를 통과하면 저장하고, 통과하지 못하면 **수치 위주 기본형**(AI 설명 없이 표만)으로 대체한다.
5. 요청별로 회원 메일 주소를 조회해 발송하고 상태를 `sent` 또는 `error`로 기록한다.
6. 한 요청이 실패해도 나머지는 계속 처리한다. `error` 요청은 회원이 화면에서 다시 요청할 수 있다(한도 내).

**표 `member_stock_reports`** (종목·날짜별 리포트 보관, 회원 정보 없음)
`stock_code`, `report_date`, `body_html`, `body_text`, `generated_at`, `used_ai boolean`
→ 기본 키 `(stock_code, report_date)`. 회원은 이 표를 직접 읽지 않는다(서버 전용, RLS만 켜고 정책 없음).

## 6. 리포트 내용과 안전장치 (상승률 Top10 수준)

**구성 (메일 본문)**
1. 제목: `[만조] 종목명(코드) 현재 상태 리포트 — 기준일`
2. 한 줄 요약 (사실 문장만: 예 "종가가 20일선보다 3.2% 위에 있습니다")
3. 가격·차트 위치: 종가, 5/20/60/120일선 대비 %, 52주 고가·저가 대비 %, 이동평균 정배열 여부 — **수치 표**
4. 거래·수급 흐름: 최근 거래대금과 투자자별 순매수(가능한 범위, 출처·기준일 표기)
5. 최근 뉴스: **제목·출처·날짜·원문 링크만**(본문 복사 금지 — 기존 계획서 7-3c와 동일)
6. 이 흐름에 대한 AI 설명(2~4문단): "무슨 일이 있었고 수치가 어떤 상태인지"를 설명
7. 맨 아래 면책: "본 메일은 공개된 정보를 정리한 것이며 투자 권유·자문이 아닙니다. 투자 판단과 책임은 본인에게 있습니다." + "회원님이 직접 요청해 발송된 메일입니다."

**금지 규칙 (AI 지시문 + 코드 검사 두 겹)**
- 지시문: 매수·매도·보유·손절·목표가·전망·추천·"오를/내릴 것" 등 **판단·예측 표현 금지**, 근거 있는 과거·현재 사실만.
- 코드 검사: 생성 결과에 금지어 목록(정규식)이 하나라도 있으면 **불합격 → 재생성 1회 → 그래도 불합격이면 수치 위주 기본형으로 대체**.
- 검사 규칙은 테스트 파일로 남기고, 금지 문장이 섞인 가짜 결과를 넣어 **반드시 걸러지는지** 확인한다.
- 숫자는 AI가 쓰지 않는다: 표의 수치는 DB 값을 코드가 직접 채우고, AI는 설명 문장만 쓴다(수치 환각 방지).

## 7. 메일 발송 (요구 4)

- **서비스:** Resend 권장 (개발자용 메일 API, 무료 구간 있음 — 한도·요금은 구현 직전에 공식 문서로 재확인).
- **키 보관:** `RESEND_API_KEY`는 **GitHub Actions 비밀값**에만 둔다. 코드·채팅·이 문서에 값을 적지 않는다.
- **보내는 주소 문제 (회장님 결정 필요):** 임의 수신자에게 보내려면 **본인 소유 도메인**을 인증해야 합니다
  (`manzo-site.vercel.app`은 불가). 도메인이 없으면 시험 단계에서는 회장님 본인 계정으로만 발송 가능합니다.
- **수신자:** 요청한 회원의 로그인 이메일 (서버가 발송 시점에 조회). 화면에는 마스킹(`a***@gmail.com`)으로 안내.
- **성격:** 회원이 직접 누른 건에 대한 1회성 안내 메일이며, 광고·홍보 문구는 넣지 않는다.
- **실패 처리:** 발송 실패 → `error` + 짧은 사유. 같은 요청을 자동 재시도하지 않고(중복 발송 방지) 회원이 다시 요청한다.
- **시험용 가짜 발송기:** 코드에 "메일 보내기" 부분을 교체 가능한 함수로 분리해, 테스트에서는 실제 발송 없이 내용만 기록한다.

## 8. 회원 화면 (My page)

- 보유/관찰 표의 각 종목 행 끝에 **[리포트 받기]** 버튼. `member_has_report_access()`가 true인 회원에게만 보인다.
- 누르면 확인 창: "`a***@gmail.com`으로 리포트를 보낼까요? (오늘 남은 횟수 2/3)"
- 버튼 상태: `받기` → `대기 중` → `생성 중` → `발송됨 (10:32)` / `실패 — 다시 시도`
- 상태는 20초마다 확인(관리자 화면의 등록 요청 폴링과 같은 방식). 하루 한도를 넘으면 버튼 비활성 + "내일 다시 요청할 수 있어요".
- 화면 하단의 기존 면책 문구는 그대로 유지.

## 9. 관리자 화면·API

- 회원 표에 `리포트 허용` 토글 (§3).
- **개인별 요청 내역은 관리자도 볼 수 없다.** 기존 원칙(회장님은 회원 개개인의 보유·매매를 보지 않는다)을 지키기 위해
  `member_report_requests`를 읽는 관리자 기능은 만들지 않는다.
- 대신 **운영 점검용 집계**만: "대기 중 N건, 가장 오래된 대기 N분, 최근 24시간 성공/실패 건수" (회원·종목 정보 없음)를
  기존 "자동화 현황" 카드에 한 장 추가. 30분 넘게 막히면 경고색.

## 10. 보안 · 개인정보 · 법률 관문 (기존 계획서 Task 7 확장)

**보안 체크 (구현 시 테스트로 증명)**
- 승인 안 된 회원이 `member_request_report`를 불러도 거부된다.
- 남의 종목·보유하지 않은 종목 코드로 요청하면 거부된다.
- 한도 초과·중복 클릭이 막힌다.
- 회원 A가 회원 B의 요청 행을 읽을 수 없다.
- 회원 브라우저로 `member_stock_reports`·메일 주소·서비스 키에 접근할 수 없다.
- 위 항목은 기존 `db/002_*_rls_test.sql` 방식(가짜 회원 2명, 트랜잭션 후 롤백)으로 `db/005_member_reports_test.sql`에 작성.

**개인정보:** 메일 주소는 요청 표에 저장하지 않고, 탈퇴 시 요청 행도 함께 삭제된다. 처리방침에 "회원이 요청한 리포트를
가입 이메일로 발송하며, 발송에 외부 메일 서비스(수탁사)를 이용한다"를 추가해야 한다(외부 수탁 고지 필요 여부는 전문가 확인).

**법률 확인 요청서에 추가할 질문** (기존 7-1에 이어서)
1. 종목 단위 "사실 정리 + 설명" 리포트를 회원 요청 시 개별 메일로 발송하는 것이 투자자문업 또는 유사투자자문업 신고 대상인지.
2. AI가 쓴 설명문을 면책 문구와 함께 보내는 것이 문제되는지, 허용되는 표현 범위.
3. 뉴스 제목·링크 인용 범위(저작권).

**공개 관문:** 위 확인이 끝나기 전에는 `reports_enabled`를 **회장님 본인 계정에만** 켠다.
일반 회원에게는 스위치를 켜지 않는 것으로 기능 전체가 차단되므로, 코드를 먼저 배포해도 안전하다.
공개는 기존 7-5와 같이 허용 회원 1명 → 3일 관찰 → 확대.
